# Lonefire（孤火）开发总计划

> 状态：**已定稿**（2026-11-15）。标注"可改"的条目是我在负责人授权下做的判断，随时可以推翻。确认后本文件是项目的总纲；各系统的细节在后续阶段的设计文档里展开。
> 标注"提案"的条目是建议，尚未由项目负责人确认。

## 1. 定位

- **一句话**：一个人在北方雪原撑过冬天。第三人称高位镜头，扁平低模风格；没有怪物，对手是寒冷、饥饿和天黑。
- **目标**：上架发售（Steam）。
- **灵感**：《荒野独居》——单人、10 件装备、主动退赛、越来越冷。
- **引擎**：Godot 4.7（本机 4.7.2）。开发平台 macOS。

## 2. 已定决策

| 事项 | 决定 |
|---|---|
| 引擎 | Godot |
| 视角 | 第三人称，高位远镜头 |
| 画风 | 风格化：纯色块、无贴图细节、冷色雪地配少量暖色 |
| 季节 | 第一版只做冬天 |
| 营地 | 帐篷或临时搭建的庇护所，不做小屋 |
| 难度 | 非轻松向：会掉体重、会死亡 |
| 结局 | 可主动退赛；退赛时排名进前几名或坚持到规定天数才有奖励，否则没有；死亡有惩罚 |
| 野兽威胁 | 第一版不做 |
| 野生动物 | 第一版要有，至少作为食物来源 |
| 平台 | 首发 macOS 和 Windows（负责人有 Windows 机器可实测）；之后手机；从一开始按多平台兼容设计 |
| 渲染器 | 先用 Forward+ 开发，移植手机时再评估 |
| 资产 | qwen-image 出概念图，混元 3D（3.0，LowPoly）出模型 |
| 积分 | 现有约 780，不够再议 |
| 仓库 | 独立仓库 `lonefire`，`ccgs` 远端指向框架 fork |
| 流程严格度 | 阶段 1–2 用 `minimal`，阶段 3 起用 `standard` |
| 资产清单 | 第 8 节的约 20 个模型，初步认可 |

## 3. 设计支柱

1. **冷与暖**：体温是核心资源；暖色在画面里就代表安全（火、庇护所）。
2. **亲手做**：生火、搭棚、处理猎物都是多步骤的过程。
3. **慢压力**：一天比一天冷，靠准备而不是反应。
4. **独处**：没有 NPC；用日记记录；走还是留由玩家自己决定。

任何功能如果不服务于这四条之一，默认不做。

## 4. 核心规则（提案，细节在阶段 3–4 的设计文档里定）

- **四项短期需求**：体温、水分、体力（含睡眠）、饱腹。
- **体重是长期资源**：每天按热量收支增减；体重越低，耐寒、体力和负重越差；低于阈值触发医疗撤离。
- **失败**：失温、脱水、体重过低（医疗撤离）。医疗撤离按"死亡"一类结算。
- **主动退赛**（已定）：随时可以结束这一局。只有两种情况有奖励：退赛时排名进入前几名，或已坚持到规定天数；否则没有奖励。
- **死亡**（已定）：有惩罚。惩罚的具体内容在阶段 4 定。
- **排名怎么产生**（可改）：模拟参赛者。每局有 9 名看不见的对手，按概率分布陆续退赛，游戏里只以通知出现（"又一人退赛，还剩 N 人"）。不需要服务器，节目感强。联网排行榜留到上线后。
- **核心抉择**：再撑一天去够名次或天数门槛，还是现在安全退赛。
- **存档**（可改）：单一自动存档，不能读档回退。否则死亡惩罚可被读档绕开。

## 5. 范围

### 第一版包含

- 一张约 200 米见方的湖岸林地，冬天。
- 移动与镜头；采集（砍柴、捡拾）；背包与开局 10 件装备选择。
- 生火（多步骤）；庇护所（至少两个搭建阶段）。
- 四项需求加体重；昼夜；天气（降雪、大风、寒潮）。
- 食物：冰钓（鱼）、陷阱（野兔）、狩猎或陷阱（松鸡）、少量采集。动物只有游荡和逃跑两种行为。
- 日记；天数计分与排名；主动退赛与死亡两种结局；局外奖励。
- 设置菜单、键鼠和手柄、中英文。

### 第一版不做

- 狼、熊等有威胁的野兽；季节变化；多人；剧情与 NPC；多张地图；深合成树。

### 上线后候选

- 野兽威胁；秋季开局；第二张地图；手机版。

## 6. 多平台约束（从第一天起遵守）

1. **渲染器**（已定）：先用 Forward+ 开发。移植手机时再评估是否切到 Mobile 渲染器（引擎参考文档对它的描述是"为手机和低端设备优化，功能有限"），届时画面可能需要调整。
2. **输入**：一律走输入动作，不写死按键。三套方案：键鼠、手柄、触屏。核心交互限定为"移动 + 一个情境动作 + 一个菜单"，不依赖悬停和右键。
3. **界面**：随分辨率缩放；按钮按手指尺寸设计；支持 16:9 到手机长屏以及 4:3。
4. **性能预算**：单个资产不超过约 3000 三角面（现有资产约 1500）；贴图不超过 1024；植被用实例化；阴影和粒子分档。
5. **存档**：平台无关的格式，带版本号。
6. **不引入原生插件**（第一版）。
7. **文本**：所有界面文字从一开始就走翻译表。

## 7. 阶段与过关标准

每个阶段不过关不进入下一个。

| 阶段 | 产出 | 过关标准 | CCGS 命令 |
|---|---|---|---|
| 0. 立项与管线 | 仓库、生成管线（已完成）；色块归类重做；修 Godot MCP；项目配置 | 现有资产都能干净地转成纯色块 | `/start`、`/setup-engine` |
| 1. 画面定调 | art bible 前 4 节；营地小景（庇护所、篝火、人物、脚印、松林） | 负责人看截图认可 | `/brainstorm`、`/art-bible` |
| 2. 手感原型 | 角色移动、镜头、砍柴、生火、昼夜与体温；人物绑骨与动画验证；键鼠加手柄 | "天黑前生起火"十分钟好玩；人物动画可接受 | `/prototype --path engine` |
| 3. 核心循环 | 需求与体重、庇护所、食物与动物、天气、背包、存档 | 能完整活过三天，且有饿死或冻死的真实风险 | `/map-systems`、`/design-system`、`/create-architecture`、`/dev-story` |
| 4. 完整一局 | 逐日变冷的难度曲线、10 件装备、日记、两种结局、局外解锁、新手引导 | 从开局到结局完整一局，外人不需要讲解就能玩 | `/create-stories`、`/dev-story` |
| 5. 打磨与内测 | 音效、特效、界面、设置、中英文、性能、平衡；Windows 实机测试 | 至少 5 个外部试玩者，无阻断问题；macOS 和 Windows 都能完整跑一局 | `/team-polish`、`/perf-profile`、`/balance-check`、`/playtest-report` |
| 6. 发售 | 商店页、试玩版、宣传片与截图、定价、macOS 和 Windows 打包签名 | 发售检查清单全过 | `/release-checklist`、`/launch-checklist`、`/team-release` |
| 7. 上线后 | 修复、候选内容、移植 | — | `/hotfix`、`/patch-notes` |

**流程严格度**：阶段 1–2 用 `minimal`（原型，少文档）；从阶段 3 起切到 `standard`（每个系统有设计文档，关键技术决定有 ADR）。项目周期长、会话多，文件是唯一可靠的记忆。

## 8. 资产计划与积分预算

**原则**

- 先出概念图，看过合格再花积分生模型。
- 每个资产的提示词、用色、尺寸记在清单里，可重跑。
- 色块归类从"每个面一种颜色"改为"把贴图本身量化成色板色"。
- 形状简单的东西用脚本直接建模，不花积分：原木、木柴、树桩、木杆、冰洞、雪堆、脚印、火焰、烟。
- 手持小工具（刀、打火棒、鱼线等）在高位远镜头下看不清，只做 2D 图标，不做模型。

**需要生成的模型（共约 20 个）**

| 状态 | 资产 |
|---|---|
| 已生成（4） | 雪松、枯树、人物、防水布庇护所 |
| 概念图已有，模型待生成（2） | 篝火石圈、石头 |
| 阶段 2–3（8） | 带雪灌木、第二种树（桦树）、大岩石、野兔、松鸡、鱼、锅与三脚架、睡袋铺位 |
| 阶段 3–4（6） | 晾肉架、陷阱、冰钓架、二阶段庇护所、营地装备堆、倒木地标 |

**预算**：剩余 16 个模型约 400 积分；现有约 780，留出约 380 给重做和追加。2D 图标约 40 张走生图额度，不占 3D 积分。

**人物动画**：混元给的是静态模型，绑骨和动画不在积分里。阶段 2 最先验证自动绑骨方案；备选是远镜头下的简单程序动画。

## 9. 技术方案要点

- 玩法数值全部放数据文件，不写死在代码里。
- 系统之间用信号通信，界面不直接引用玩法代码。
- 关键决定各写一份 ADR：渲染器、输入抽象、存档格式、数据驱动的物品与配方。
- 写任何引擎 API 之前查 `docs/engine-reference/godot/`（模型知识早于 4.7）。
- 任何玩家可见的改动都要实际运行并截图存证。

## 11. 风险

| 风险 | 应对 |
|---|---|
| 人物动画质量 | 阶段 2 最先验证；有程序动画备选 |
| AI 贴图自带阴影，色块归类不准 | 阶段 0 用多个资产一起调；改为贴图量化 |
| 范围膨胀 | 支柱筛选；不做清单；阶段过关标准 |
| 模型对 Godot 4.7 知识不全 | 查引擎参考文档 |
| AI 判断不了"好不好看" | 每个画面节点由负责人看截图拍板 |
| 积分不够 | 20 个模型的上限清单；程序建模和 2D 图标分流 |
| 手机移植时画面或性能不达标 | 先用 Forward+，移植时再评估渲染器；从一开始守性能预算 |
| 非轻松向劝退新玩家 | 阶段 4 做新手引导；阶段 5 外部试玩 |

## 12. 开工时由我决定的事项（可改）

1. **排名**：模拟参赛者，9 名对手，无服务器（第 4 节）。
2. **存档**：单一自动存档，不可读档回退（第 4 节）。
3. **市场与设定**：面向全球，界面首选英文并提供中文；地点为泛指的北方针叶林荒野，不绑定具体地域，动植物选用松、桦、兔、松鸡、鳟鱼这类跨地域常见物种。
4. **时间**：不设发售日期，按阶段过关推进；范围已按积分和单人开发压到最小。
5. **远端备份**：暂时只在本地。负责人建好私有仓库后接上。
6. **参考图**：按现有那张白天雪景的风格延伸；夜晚和火光的方向在阶段 1 出两版给负责人选。

## 13. 开工顺序

1. 核实 qwen-image 与混元 3D 的商用条款（阻断项：结果决定资产管线能否用于发售）。
2. 色块归类改为贴图量化，用 4 个已生成资产验证。
3. 生成剩余 2 个概念图已就绪的模型（篝火、石头）。
4. 搭营地小景，产出画面定调截图交负责人确认。
